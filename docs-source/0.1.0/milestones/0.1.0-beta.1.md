# Aellux 0.1.0 Beta 1

**Status:** Concluído
**Versão alvo:** `0.1.0-beta.1`

> `#` indica implementação existente ou trabalho em andamento que ainda precisa de revisão ou validação.

## Objetivo geral

Validar o runtime, o sistema de extensões e a compatibilidade progressiva do Aellux em aplicações Web existentes, incluindo integração segura com Bootstrap, carregamento seletivo de extensões e um fallback Legacy com funcionamento mínimo em ES5.

## Conclusão

### Avaliação geral

O Aellux `0.1.0-beta.1` alcançou um estado coerente para validação pública controlada. O projeto já possui uma arquitetura identificável, um contrato de extensões documentado, distribuições Modern e Legacy, ciclo de vida previsível e cenários automatizados para os fluxos centrais. A separação entre boot, orchestrator, Extensions e helpers reduz o acoplamento e permite evolução incremental sem concentrar todos os comportamentos em um único bundle.

O estado atual é adequado para testes beta, aplicações internas, protótipos avançados e pilotos públicos com versão fixada e monitoramento. Ainda não deve ser apresentado como uma plataforma estável para aplicações críticas ou como compatível com uma matriz ampla de navegadores sem validação adicional do consumidor.

### Pontos fortes

- **Arquitetura modular:** o boot permanece pequeno e responsável pela seleção do runtime; o orchestrator coordena carregamento e lifecycle; cada Aellux Extension mantém uma responsabilidade funcional própria.
- **Integração progressiva:** Extensions podem ser declaradas por JavaScript ou HTML, carregadas de forma eager ou lazy e aplicadas a conteúdo inserido dinamicamente por meio de `$ae.update(root)`.
- **Lifecycle explícito:** `init`, `mount`, `unmount` e `destroy` possuem responsabilidades distintas. A montagem é idempotente nos cenários testados e a desmontagem remove listeners e recursos associados aos elementos.
- **Isolamento de falhas:** falhas de carregamento, inicialização, montagem ou destruição são encaminhadas ao sistema de diagnostics sem necessariamente impedir o início das demais Extensions.
- **Compatibilidade progressiva:** o boot seleciona runtime Modern ou Legacy, o Core publica variantes correspondentes e o contrato `builds` diferencia Extensions Modern-only, Legacy-only ou com ambas as variantes.
- **Contrato para terceiros:** scaffold, convenções de nomes, `mountMap`, builder de referência, polyfills disponíveis e responsabilidades de uma Extension externa estão documentados.
- **Distribuição reproduzível:** o build gera arquivos individuais, orchestrator, bundle completo, variantes minificadas, source maps, CSS adaptativo e saídas Legacy.
- **Cobertura funcional inicial:** 17 cenários de navegador cobrem lifecycle, carregamento eager/lazy, estilos, falhas isoladas, Bootstrap, seleção de runtime e variantes de Extensions.
- **Postura de integração:** Aellux utiliza namespaces próprios e não depende de Bootstrap, permitindo uso com HTML puro ou coexistência com sistemas visuais existentes.

### Pontos fracos e limitações atuais

- **Maturidade de API:** esta é uma beta inicial. Os contratos públicos ainda podem mudar e não existe uma política formal de depreciação ou compatibilidade entre versões.
- **Cobertura concentrada:** os testes atuais são cenários de integração executados em um navegador Chromium disponível localmente. Não existe ainda uma matriz automatizada para Chrome, Edge, Firefox, Safari e navegadores móveis.
- **Legacy parcialmente comprovado:** o modo Legacy forçado valida seleção, carregamento e sintaxe gerada, mas não substitui testes em ambientes antigos reais. ES5 e polyfills não garantem suporte irrestrito a qualquer navegador histórico.
- **Ausência de CI:** o repositório não possui pipeline versionado para executar build, testes de navegador e verificação do pacote a cada alteração ou pull request.
- **Ausência de testes unitários e métricas:** não há suíte unitária, relatório de cobertura, orçamento de tamanho, benchmark de inicialização ou teste prolongado de consumo de memória.
- **Bootstrap com escopo limitado:** a cobertura atual comprova coexistência básica de CSS, classes e montagem. Ela não representa uma garantia completa para todos os componentes JavaScript, plugins, modais, offcanvas, tooltips ou sequências assíncronas do Bootstrap.
- **Dependência externa em teste:** o cenário de Bootstrap utiliza recurso remoto e pode depender de conectividade e disponibilidade do CDN.
- **Experiência de desenvolvimento ainda básica:** não há declarações TypeScript, validação estática da API das Extensions ou ferramenta dedicada para verificar automaticamente o contrato de um pacote de terceiros.
- **Distribuição Legacy maior:** os polyfills compartilhados aumentam significativamente o tamanho do runtime Legacy; ainda não existe orçamento público de desempenho ou tamanho.

### Pontos de atenção antes da tag

- O índice lazy é protegido contra carregamentos concorrentes pela Promise armazenada, mas atualmente é removido após a inicialização bem-sucedida. A redação que exige remoção exatamente no início do carregamento deve ser alinhada ao comportamento real ou implementada literalmente.
- A documentação e a comunicação pública devem distinguir “sintaxe ES5 com polyfills definidos” de “suporte a navegadores antigos”.
- A compatibilidade Bootstrap deve ser divulgada com o escopo efetivamente testado, evitando uma promessa genérica para todo o framework.
- Extensions de terceiros que omitirem `builds` assumem o compromisso de publicar variantes Modern e Legacy; documentação e diagnostics reduzem o risco, mas não impedem uma declaração incorreta do autor.
- A API global `Aellux`/`$ae` facilita integração por script clássico, porém exige atenção a conflitos globais, ordem de carregamento, CSP, URLs relativas e políticas de cache.
- O modo `full` deve continuar sendo monitorado para evitar crescimento indiscriminado do bundle; Extensions especializadas devem permanecer opt-in quando não forem essenciais ao Core.

### Garantias oferecidas pela beta

Dentro dos cenários, dependências e artefatos versionados deste repositório, a beta garante:

- geração bem-sucedida das distribuições atualmente definidas por `npm run build`;
- boot ES5 capaz de selecionar entre as distribuições Modern e Legacy;
- runtime Modern com baseline de sintaxe ES2017+ e detecção das APIs exigidas;
- variantes Legacy do Core transpiladas para ES5 e executadas após os polyfills compartilhados;
- registro e carregamento de Extensions eager, lazy, com CSS, sem CSS e com perfis de build declarados;
- lifecycle idempotente e liberação de recursos nos cenários automatizados;
- falha isolada de uma Extension sem bloquear necessariamente o orchestrator e as demais Extensions;
- geração do CSS adaptativo a partir da configuração da Adaptive Extension;
- aprovação dos 17 cenários presentes em `tests/browser/` no ambiente Chromium usado durante a preparação da versão;
- disponibilidade do código sob Apache License 2.0.

Estas garantias não incluem estabilidade até `1.0.0`, ausência total de defeitos, compatibilidade universal, desempenho para qualquer escala, segurança de aplicações consumidoras ou funcionamento de APIs que não estejam cobertas pelo Core e seus polyfills documentados.

### Necessidades para uso comercial público

Para uso comercial controlado, recomenda-se fixar exatamente a versão, executar os testes no conjunto real de navegadores do produto, manter fallback de interface sem JavaScript, monitorar diagnostics e validar cada Extension adicional de forma independente.

Antes de recomendar Aellux para uso público amplo ou aplicações críticas, são necessários pelo menos os seguintes avanços:

1. **CI obrigatória:** executar build, testes de navegador, verificação do pacote e busca de referências obsoletas em cada alteração.
2. **Matriz de navegadores:** validar Chromium, Firefox e WebKit em desktop e mobile, além de ambientes Legacy explicitamente suportados.
3. **Testes complementares:** adicionar testes unitários para helpers e contratos, testes de regressão, carga, navegação prolongada, BFCache e detecção de vazamentos de memória.
4. **Bootstrap completo:** manter fixtures locais versionadas e testar componentes JavaScript, conteúdo revelado dinamicamente e coexistência de listeners sem depender exclusivamente de CDN.
5. **Segurança e cadeia de fornecimento:** executar auditoria de dependências, definir política de atualização, publicar processo de reporte de vulnerabilidades e avaliar CSP, SRI e proveniência dos artefatos.
6. **Conformidade de licenças:** revisar as licenças dos polyfills e dependências incorporadas ao bundle e publicar os avisos exigidos para redistribuição comercial.
7. **Governança de API:** definir SemVer, política de suporte, janela de depreciação, critérios para promoção de Extensions ao Core e processo de revisão de contribuições externas.
8. **Desempenho:** estabelecer limites para tamanho dos bundles Modern e Legacy, tempo de boot, trabalho agendado de layout e custo de `$ae.update(root)` em documentos grandes.
9. **Acessibilidade:** validar que Extensions e estados visuais preservam foco, semântica, navegação por teclado, leitores de tela e preferências do usuário.
10. **Publicação operacional:** automatizar release, tag, pacote npm, checksums ou integridade para CDN, documentação versionada e procedimento de rollback.
11. **Suporte ao consumidor:** definir navegadores suportados, canal de issues, severidade de incidentes, política de manutenção e responsabilidades entre Core, Extensions oficiais e Extensions de terceiros.

### Parecer final

O projeto está pronto para ser apresentado como **beta pública experimental**, com arquitetura e contrato suficientes para receber integração e feedback externos. Está também apto a uso comercial limitado quando a aplicação consumidora assume a validação da sua própria matriz, fixa a versão e mantém alternativas de degradação. Para uso comercial público amplo, especialmente em fluxos críticos, ainda são necessários CI, matriz multi-browser, validação Legacy real, auditoria de segurança e licenças, metas de desempenho e governança formal de releases.
