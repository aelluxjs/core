# Policy Decisions Pending Review — AelluxJS 0.1.x

**Status:** Non-normative maintainer review. These proposals do not create support obligations or authorize exceptions.

The [Compatibility Commitment](../docs-source/0.1.x/runtime/compatibility-commitment.md) establishes the requested minimum public-contract protection beginning with `0.1.0`. This review separates that commitment from policies not previously established by the repository. The package remains `0.1.0-beta.10`; neither this document nor the commitment promotes the release or approves publication.

The line-wide preservation rule, reservation of intentional Stable breaks for `0.2.x`, and conservative retention of deprecated Stable APIs in `0.1.x` are formalized by the requested commitment. They were not already established merely by a beta's Stable label. Historical beta changelogs are migration evidence, not a retroactive compatibility promise.

## Decisions requiring maintainer approval

| Decision | Existing state | Proposal for review | Until approved |
| --- | --- | --- | --- |
| Security / severe-defect exceptions | The repository describes trust boundaries and validation, but has no general exception policy. | Require impact analysis, a compatible mitigation when feasible, explicit maintainer approval, affected-version disclosure, migration guidance and targeted validation before an exceptional Stable break. | No blanket exception. Review each concrete case explicitly; documenting a change alone does not approve it. |
| Maintenance focus and backports | No release support window or backport schedule is defined. | Concentrate fixes on the latest `0.1.x`; backport selectively when the maintainer decides it is warranted. | No simultaneous-maintenance obligation for all patches, no end date, and no promised correction SLA. |
| Vulnerability reporting | A dedicated channel remains a post-release task in the milestone; package metadata lists the public issue tracker for ordinary bugs. | Choose and publish a private reporting route and disclosure process before claiming that one exists. | No invented private channel, response deadline or security support window. |
| Deprecation notice and experimental promotion | The milestone leaves the broader policy and promotion criteria open. | Keep the commitment's in-line Stable retention rule; separately define notice practices, replacement criteria and evidence required to promote experimental APIs. | No fixed number of releases or days, automatic promotion, indefinite support, or permission to demote an existing Stable contract. |
| npm release / withdrawal procedure | The milestone still requires immutable version publication, package inspection and correction/withdrawal procedures. | Approve that operational process independently of API preservation. | No npm publication, tag, version bump, CDN rollout or withdrawal is authorized by completing this document. |

These decisions must be resolved explicitly before presenting their proposals as adopted policy. They do not block drafting, linking or validating the requested documentation locally.

## Contract discrepancies found during inspection

| Area | Evidence | Handling in this documentation change |
| --- | --- | --- |
| Historical Focus / Point delivery notes | Several completed milestone entries describe separate delivery outside Full. Current `src/aellux.full.js`, the Extension index and individual guides include both in Full. Both remain Not stable. | Clarify that those milestone entries describe earlier delivery. The commitment uses current distribution without changing stability or runtime code. |
| Feedback easing hook | The [Feedback guide](../docs-source/0.1.x/core-extensions/feedback.md) documents setting `--ae-feedback-aellux-ease` as an application input. `scripts/semantic-definitions.mjs` groups it among private properties with `role: "internal"`. | Record the conflicting classification for an explicit metadata/documentation decision. The commitment does not use this hook as an internal example or silently withdraw its documented application usage. No metadata or functional change is included. |
| Editor catalog counts | The editor guide's numeric coverage summary is a historical snapshot; the generated catalog and definitions contain newer entries. | Use actual named entries and roles rather than treating those counts as a compatibility or completeness guarantee. No catalog regeneration is needed for this documentation-only change. |

No production-code correction is part of this review. Any later resolution that changes behavior requires its own implementation and validation scope.
